# Aéza Analyzer — сценарий живой демонстрации

> **Сверено 2026-10-23.** Числа в файле соответствуют текущей конфигурации
> (`expiry_proximity = 3,0`, горизонт 30 дней, окно отказов 90 дней): балл
> клиента #10 — **71,4**, выручка под риском — **5,80 €**. Прежняя конфигурация
> (`expiry_proximity = 15,0`) давала 73,3 и 5,74 € — если увидите эти числа,
> файл устарел.
> Команда запуска backend — `python -m uvicorn main:app` **из корня репозитория**
> (`app.main:app` из `backend/` падает с `ModuleNotFoundError: core`).
> Публичный стенд — <https://aeza-sentinel.pixel-minds.ru/> (проверен: `GET /health`
> → `{"status":"ok"}`, `/api/v1/openapi.json` → «Aéza Analyzer» 2.0.0).
> Адреса `*.prod-runtime.all-hands.dev` — временные адреса песочницы; для защиты
> не используйте.
> Актуальные значения и команды: `README.md`, `docs/PROJECT_GUIDE.md`,
> `docs/AI_ANALYST.md`.

Обязательный сценарий организатора: **найти клиента под риском → объяснить причины →
показать денежную оценку → изменить коэффициент → показать обновление результата.**

Регламент: 4–6 минут доклада. Демонстрация идёт параллельно слайдам 03–08.

## Подготовка за 10 минут до защиты

1. Поднять стек по README (backend + frontend) и убедиться, что снимок загружен:
   ```bash
   # из КОРНЯ репозитория (рабочая точка входа — корневой main.py)
   export AEZA_DATABASE_URL="sqlite:///$(pwd)/data/analytics.sqlite"
   export AUTH_DATABASE="$(pwd)/db/auth.sqlite3"
   export AUTH_PRIVATE_KEY="$(pwd)/db/private_key.pem"
   export AEZA_ANALYTICS_FACTORY="backend.app.domain.module:create"
   export AEZA_SEED_DEMO_DATA=1
   python -m backend.users create analyst@aeza.test   # пароль дважды, минимум 12 символов
   python -m uvicorn main:app --host 127.0.0.1 --port 8000
   # во втором терминале:
   cd frontend && npm install && npm run dev   # http://127.0.0.1:5173
   ```
   Полный стек с PostgreSQL — `docker compose up --build` (интерфейс `:8080`).
   Учётная запись создаётся **вручную**: приложение не заводит администратора при
   старте. Пароль вводится в консоли и не хранится в конфигурации.
2. Открыть два окна браузера и войти под учётной записью, созданной командой
   `backend.users create` (в демо-среде — `analyst@aeza.test`):
   - окно A: демо-стенд — для показа (публичный адрес
     `https://aeza-sentinel.pixel-minds.ru/`, HTTP 200; `GET /health` → `{"status":"ok"}`,
     `GET /api/v1/openapi.json` → «Aéza Analyzer» 2.0.0, 28 путей);
   - окно B: тот же стенд — резерв, если окно A потеряет состояние.
   Адрес стенда временный: перед защитой подставьте актуальный URL и замените
   заглушку `[QR-КОД: ДЕМО]`.
3. Вернуть модель к значениям по умолчанию: `/settings` → **«Значения по умолчанию»**.
   Убедиться, что вес `expiry_proximity` = **3** и балл клиента #10 = **71,4**.
4. Открыть заранее во вкладках: `/customers`, `/customers/10`, `/settings`.
5. Проверить, что в шапке дашборда стоит опорный момент **19.10.2026, 15:00 UTC**
   и горизонт **30 дн.** Если дата другая — данные переимпортированы, числа будут
   отличаться от слайдов. Это единственный критичный параметр воспроизводимости.
6. Масштаб браузера — 100 %, окно на весь экран. Скрыть закладки и лишние вкладки.

## Сценарий по шагам

### Шаг 1. Найти клиента под риском — 40 сек

| Действие | Что говорите |
|---|---|
| Открыть `/customers` | «Список уже отсортирован по риску. Наверху — максимальный балл.» |
| Показать строки `user-0005@example.test` и `user-0010@example.test` | «Клиенты #5 и #10 делят максимум: 71,4 из 100, категория высокий. Берём #10 — его причину видно на уровне услуги.» |
| Показать колонки «Услуги 3 / 3», «Выручка под риском 0,00 €» | «Три услуги, все пригодны для прогноза. Выручка под риском — ноль, объясню почему через минуту.» |

Слайд в этот момент: **04 «Клиент #10 — высокий риск, 71,4 из 100»**.

### Шаг 2. Объяснить причины — 60 сек

| Действие | Что говорите |
|---|---|
| Кликнуть строку → карточка `/customers/10` | «Открываем профиль.» |
| Показать метрики: балл 71,4, категория высокий, 2 из 3 услуг высокого риска | «Балл клиента — максимум по услугам, пригодным для прогноза. Среднее замаскировало бы критичные услуги.» |
| Блок «Причины оценки» по `service-0030` | «Вот почему: услуга просрочена на 35 дней, два продления из двух не выполнены, автопродление выключено.» |
| Нажать **«Показать все факторы (7)»** | «Формула открыта: 100 умножить на сумму вес×значение, делить на сумму весов. Здесь 7,5 из 10,5 — отсюда 71,4.» |
| Показать факторы с вкладом 0,00 | «Два фактора дали ноль: баланса хватает, услуга не приостановлена. Модель не накручивает риск там, где сигналов нет.» |

Слайд: **05 «Балл объясним: видно каждый вклад»**.

Ограничение, которое нужно сказать вслух: балл — не вероятность оттока, а индекс
rule-based модели. Исторических исходов ухода в снимке нет, поэтому точность не измерена.

### Шаг 3. Денежная оценка — 40 сек

| Действие | Что говорите |
|---|---|
| Показать блок «Выручка под риском 0,00 €» у клиента #10 | «Балл высокий, а денег под риском ноль. Все его сроки уже прошли: горизонт смотрит вперёд, а просрочка — в прошлом.» |
| Открыть `/` → таблица «Ближайшие продления в горизонте» | «По всей базе в горизонт попадают четыре продления: 0,36 + 0,70 + 1,81 + 2,93 = 5,80 €.» |
| Показать метрику «Выручка под риском 5,80 €» | «Это прогнозная экспозиция: стоимость продления, умноженная на балл риска. Предстоящие продления без учёта риска — 17,03 €.» |
| Показать «Исторические пополнения 22 240,73 €» | «Это справочная история и баланс клиентов. Мы их не складываем с прогнозом и не называем потерями.» |

Слайд: **07 «Риск и деньги — разные величины»**.

### Шаг 4. Изменить коэффициент — 50 сек

| Действие | Что говорите |
|---|---|
| Открыть `/settings` | «Проверим гипотезу. Усилим фактор «близость даты окончания» — сейчас вес 3.» |
| Сформулировать ожидание **до** изменения | «Ожидаю, что баллы вырастут и услуг высокого риска станет больше.» |
| Ввести **9** в поле `expiry_proximity` → **«Сохранить»** | «Меняю вес и сохраняю.» |
| Показать «Сумма весов» | «Сумма весов выросла сразу: 13,0 → 19,0. Фактор помечен «изменено».» |
| Ничего не нажимать | «Сводка пересчитывается на бэкенде и подтягивается сама — страницу не перезагружаю.» |
| Показать метрики в шапке настроек | «Услуг высокого риска: 4 → 7. Выручка под риском: 5,80 → 7,72 €.» |

**Проверено на стенде (Playwright, без перезагрузки):** сразу после «Сохранить» сумма
весов меняется 13,0 → 19,0, а карточки сводки обновляются на месте: услуг высокого
риска 4 → 7, выручка под риском 5,80 → 7,72 €. Категории клиентов при этом не
сдвигаются (высокий 3, средний 3) — это тоже честный результат, и его стоит показать.
URL не меняется, страница остаётся открытой. Расчёт выполняет сервер; интерфейс сам
перечитывает сводку, ручной перезагрузки не требуется.

Слайд: **08 «Меняем вес — результат пересчитывается»**, левая половина.

### Шаг 5. Доказать, что результат изменился — 40 сек

| Действие | Что говорите |
|---|---|
| Открыть `/customers/10` | «Тот же клиент: балл 71,4 → 81,8.» |
| Показать блок факторов | «Вес фактора вырос с 3,0 до 9,0, а сумма весов по этой услуге — с 10,5 до 16,5. Вклад фактора теперь 9,0. Отсюда 100 × 13,5 / 16,5 = 81,8.» |
| Вернуться в `/settings` → **«Значения по умолчанию»** | «Настройка сохраняется на сервере, поэтому возвращаем исходные значения — балл снова 71,4.» |
| Открыть `/customers` | «И порядок списка вернулся: #5 и #10 снова с 71,4.» |

Слайд: **08**, правая половина.

**Важно:** пересчёт автоматический. Отдельной кнопки «Пересчитать» в продукте нет —
бэкенд пересчитывает аналитику при сохранении настроек. Не искать эту кнопку на защите.

### Шаг 6. Бизнес-вывод — 25 сек

«Что это даёт команде Aéza: приоритизированный список вместо ручного просмотра,
объяснение вместо непрозрачного числа, денежную оценку отдельно от баланса и
возможность проверить гипотезу за десять секунд. Мы не обещаем автоматического
удержания — продукт помогает решить, с кого начать.»

Слайд: **09 «Команда видит, с кого начать»**.

## AI-аналитик (если спросят или если есть время) — 40 сек

Обязательным сценарием организатора AI не является, но это сильный ответ на вопрос
«почему rule-based, а не ML». Показывать по слайду **06 «Числа считает движок — AI их
объясняет»**, при наличии сети — живьём на `/ai`.

| Действие | Что говорите |
|---|---|
| Открыть `/ai` | «AI не считает балл — он объясняет уже посчитанный результат.» |
| Ввести: «Объясни, почему у клиента #10 высокий балл риска, и назови главные факторы» | «В контекст уходят только факты движка и локальная документация.» |
| Дождаться ответа (40–90 с на CPU) | «Вот ответ и ссылки на источники под ним.» |
| Показать блок «ИСТОЧНИКИ» | «Модель обязана ссылаться на конкретные данные и документы.» |
| Задать вопрос с несуществующим числом | «Если модель называет число вне фактов, оно удаляется автоматически — это видно в интерфейсе.» |

**Что сказать:** «Это не витрина «у нас есть AI». Модель — слой объяснения поверх
прозрачной формулы; если она недоступна, аналитика продолжает работать.»

**Возможные вопросы:**
- «Данные уходят наружу?» — Нет. Провайдер только loopback, внешние AI-API не
  используются, персональные данные не пишутся в логи.
- «Какая модель?» — `qwen2.5:3b-instruct` через Ollama, на CPU.
- «Что если модель недоступна?» — `503` и понятный текст; аналитика работает.

**Подготовка:** backend с AI должен быть запущен до защиты (`ollama serve` + модель
загружена). Если AI не поднят — показывайте только слайд 06, не открывайте `/ai`.

## Что делать, если что-то сломалось

| Ситуация | Решение |
|---|---|
| Балл #10 не 71,4 | Настройки изменились. `/settings` → «Значения по умолчанию». Если не помогло — данные переимпортированы, используйте слайды 04–08 как источник чисел и говорите «на момент снятия снимка». |
| Дата в шапке не 19.10.2026 15:00 UTC | Снимок перезалит. Числа на слайдах больше не совпадут с экраном. Показывайте слайды, а не интерфейс, и скажите об этом прямо. |
| Интерфейс не отвечает | Переключитесь на резервное окно B. Если и оно молчит — проведите демонстрацию по слайдам 04–07: там те же экраны и те же числа. |
| Вопрос «какая точность модели?» | «Не измерена и не заявлена: в снимке нет истории уходов, обучать и валидировать классификатор не на чем. Модель rule-based и прозрачна.» |
| Вопрос «это макет?» | «Нет. Запущенное приложение: FastAPI + Postgres + React на снимке из комплекта кейса. Скриншоты на слайдах сделаны из него.» |
| Вопрос «что на 10 000 клиентов?» | «Список пагинируется, фильтры и сортировка выполняются в SQL. Нагрузочное тестирование мы не проводили — говорим честно.» |
| Вопрос «это настоящий AI или декорация?» | «Модель не считает балл — она объясняет посчитанный. Числа только из фактов движка; несуществующие числа удаляются автоматически. Провайдер только loopback.» |
| AI-панель не отвечает | Показывайте слайд 06 — там реальный ответ. Не изображайте работающий AI, если он не поднят. |
