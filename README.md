# Invoice Keeper

Система учёта регулярных расходов и платежей: помогает не забывать о сроках
оплаты, видеть финансовую нагрузку, контролировать задолженности и сохранять
историю фактических платежей.

Продукт рассчитан на команду: **у всех пользователей одна общая история
платежей**, а статус оплаты принадлежит платёжному периоду, а не конкретному
пользователю. Если один человек отметил платёж оплаченным, остальные видят тот
же статус.

---

## Быстрый старт (одна команда)

```bash
./run.sh          # создать .env, собрать и запустить всё
./run.sh seed     # создать демонстрационные данные
```

Откройте http://localhost:8080 и войдите администратором (учётные данные
показывает `./run.sh creds`).

Скрипт `run.sh` сам создаёт `.env` со случайным `SECRET_KEY`, поднимает стек,
ждёт готовности API и печатает адреса. Если пользователь не в группе `docker`,
он автоматически использует `sudo docker`.

| Команда | Что делает |
|---|---|
| `./run.sh` | поднять стек (сборка + миграции + bootstrap админа) |
| `./run.sh seed` | демонстрационные данные (идемпотентно) |
| `./run.sh verify` | проверить запущенный стек по HTTP (57 проверок) |
| `./run.sh test` | backend-тесты (pytest, 104 теста) |
| `./run.sh e2e` | браузерные тесты (Playwright, 42 теста) |
| `./run.sh check` | сборка, типы и линтер frontend |
| `./run.sh full` | seed + verify + test + check |
| `./run.sh creds` | показать демонстрационные учётные данные |
| `./run.sh ps` / `logs` / `down` / `reset` | состояние, логи, остановка, удаление данных |

Подробная ручная настройка — в разделах ниже.

## Возможности

- **Регулярные платежи** — аренда, серверы, подписки, лицензии. Ежемесячное,
  квартальное и годовое повторение.
- **Платёжные периоды** — каждый срок оплаты это отдельная запись со своим
  статусом. История прошлых периодов сохраняется даже после завершения платежа.
- **Корректная просрочка** — различаются состояния «ожидает оплаты», «скоро
  срок», «просрочено», «оплачено вовремя», «оплачено с просрочкой». Срок оплаты
  (`due_date`) и фактическая дата (`paid_at`) — независимые значения.
- **Общий статус для всех** — изменение статуса сразу видно всем пользователям.
- **Dashboard** — суммы по каждой валюте отдельно, счётчики просрочек и
  ближайших сроков, состояние каналов уведомлений.
- **Таблица платежей** — поиск, фильтры по статусу, валюте и диапазону дат,
  сортировка, пагинация.
- **Календарь** — реальные периоды по датам, переключение месяцев, фильтры.
- **Бюджеты** — месячные и годовые лимиты отдельно по валютам, план и факт,
  остаток и процент использования.
- **Журнал аудита** — кто, что и когда сделал (только для администратора).
- **Чеки** — ссылка или файл, привязанные к конкретному периоду.
- **Telegram-уведомления** — реальный Bot API, напоминание за 3 дня,
  inline-кнопка «Оплачено».
- **Email-уведомления** — SMTP, тот же сервис правил, что и Telegram.

Роли: `admin` (управление платежами, пользователями, бюджетами, аудит) и `user`
(просмотр общих платежей, отметка оплаты, исправление фактической даты). Все
ограничения проверяются на сервере, а не только скрытием кнопок.

## Стек

| Слой | Технологии |
|---|---|
| Backend | Python 3.13, FastAPI, SQLAlchemy 2, Alembic, Pydantic v2 |
| База данных | PostgreSQL 16 |
| Frontend | React 19, TypeScript, Vite, react-router |
| Аутентификация | Серверные сессии, cookie HttpOnly, CSRF, Argon2id |
| Фоновые задачи | Отдельный worker-процесс (outbox в PostgreSQL) |
| Уведомления | Telegram Bot API, SMTP |
| Тесты | pytest, Playwright |
| Развёртывание | Docker Compose, nginx (frontend + reverse proxy) |

Дополнительные сервисы (Redis, брокер, Kubernetes) сознательно не используются —
outbox в PostgreSQL решает задачу надёжных уведомлений без лишней инфраструктуры.
Подробнее: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Настройка `.env`

```bash
cp .env.example .env
```

Заполните обязательные значения:

| Переменная | Назначение |
|---|---|
| `SECRET_KEY` | секрет сессий. Сгенерируйте: `python -c "import secrets; print(secrets.token_urlsafe(48))"` |
| `ADMIN_PASSWORD` | пароль bootstrap-администратора |
| `ADMIN_USERNAME` / `ADMIN_EMAIL` | логин и email администратора |

Необязательные интеграции (приложение работает и без них):

| Переменная | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота |
| `TELEGRAM_CHAT_ID` | ID чата для уведомлений |
| `TELEGRAM_ALLOWED_USER_IDS` | кому разрешено нажимать «Оплачено» (пусто = всем в чате) |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_TO`, `SMTP_USE_TLS` | email-уведомления |

Прочие параметры (`APP_TIMEZONE`, `REMINDER_DAYS_BEFORE`,
`GENERATION_HORIZON_MONTHS`, `WORKER_INTERVAL_SECONDS`, `WORKER_MAX_ATTEMPTS`,
`LOGIN_RATE_LIMIT_*`, `MAX_UPLOAD_MB`) описаны комментариями в `.env.example`.

> Реальный `.env` добавлен в `.gitignore` и не должен попадать в репозиторий.

## Получение Telegram-токена

1. Откройте [@BotFather](https://t.me/BotFather) в Telegram.
2. Отправьте `/newbot`, задайте имя и username бота.
3. BotFather вернёт токен вида `123456789:AA...` — это `TELEGRAM_BOT_TOKEN`.
4. Узнайте `TELEGRAM_CHAT_ID`: напишите боту любое сообщение, затем откройте
   `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и найдите `chat.id`. Для
   группового чата ID обычно отрицательный.
5. Впишите значения в `.env` и перезапустите worker:

```bash
docker compose up -d worker
```

Чтобы ограничить круг людей, которым разрешено нажимать «Оплачено», укажите
`TELEGRAM_ALLOWED_USER_IDS` (их `from.id` из `getUpdates`).

## Настройка SMTP

Заполните `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`,
`SMTP_FROM` и список получателей `SMTP_TO`. Для TLS-порта 587 оставьте
`SMTP_USE_TLS=true`. Если `SMTP_HOST` пуст, email-канал отключён: worker не
отправляет письма и не имитирует успешную доставку, а в интерфейсе канал
отображается как «Не настроено».

## Запуск через Docker Compose

```bash
cp .env.example .env      # заполните SECRET_KEY и ADMIN_PASSWORD
docker compose up --build -d
```

Одна команда поднимает все сервисы. При старте API автоматически применяет
миграции и создаёт администратора, а worker ждёт готовности API.

Проверка состояния:

```bash
docker compose ps
curl -s http://localhost:8080/api/v1/health
```

Остановка:

```bash
docker compose down          # данные сохраняются в volumes
docker compose down -v       # ВНИМАНИЕ: удаляет базу и загруженные чеки
```

### Адреса

| Что | URL |
|---|---|
| Веб-панель | http://localhost:8080 |
| API | http://localhost:8080/api/v1/ |
| Swagger UI | http://localhost:8080/api/v1/docs |
| OpenAPI JSON | http://localhost:8080/api/v1/openapi.json |
| Healthcheck | http://localhost:8080/api/v1/health |

nginx отдаёт frontend и проксирует `/api/`, поэтому браузер работает с одним
origin и CORS не требуется.

## Миграции базы данных

Миграции применяются автоматически при старте API и worker. Вручную:

```bash
docker compose exec api alembic upgrade head     # применить
docker compose exec api alembic current          # текущая ревизия
docker compose exec api alembic history          # список ревизий
```

Повторный запуск `alembic upgrade head` безопасен.

## Bootstrap администратора

Администратор создаётся при первом запуске из переменных `ADMIN_USERNAME`,
`ADMIN_EMAIL` и `ADMIN_PASSWORD`. Пароль хешируется (Argon2id).

- Повторный запуск **не создаёт дубликат** и **не перезаписывает** пароль уже
  существующего администратора.
- Чтобы сменить пароль администратора, измените его через интерфейс управления
  пользователями (администратор) либо удалите аккаунт осознанно и создайте заново.
- Bootstrap-аккаунт защищён: его нельзя удалить или понизить в правах через
  обычный CRUD пользователей (сервер вернёт `403`).

## Создание обычных пользователей

1. Войдите администратором.
2. Откройте раздел **Пользователи**.
3. Нажмите **Добавить пользователя**, задайте логин, email, пароль и роль `user`.

Пароль должен соответствовать требованиям валидации (проверяется на сервере).
Деактивированный пользователь не может войти, его история при этом сохраняется.

## Демонстрационные данные

Данные синтетические и создаются только по явному запросу (профиль `demo`):

```bash
docker compose --profile demo run --rm seed
```

Скрипт идемпотентен: повторный запуск не создаёт дубликаты. Создаются несколько
платежей в RUB, USD и EUR, история за прошлые месяцы, оплаченные вовремя и с
просрочкой периоды, а также намеренно просроченный период.

Демонстрационные учётные данные (пароль задаётся `DEMO_PASSWORD`):

| Роль | Логин | Пароль по умолчанию |
|---|---|---|
| Администратор | `admin` | значение `ADMIN_PASSWORD` из `.env` |
| Обычный пользователь | `demo_user` | значение `DEMO_PASSWORD` из `.env` |

> Это учётные данные для локальной демонстрации. На реальном стенде смените
> пароль администратора в `.env` до первого запуска.

## Проверка сохранения данных

```bash
# до перезапуска
docker compose exec postgres psql -U invoice -d invoice \
  -c "SELECT count(*) FROM payment_occurrences;"

docker compose restart

# после перезапуска — число то же
docker compose exec postgres psql -U invoice -d invoice \
  -c "SELECT count(*) FROM payment_occurrences;"
```

Данные хранятся в volumes `postgres_data` (база) и `uploads_data` (чеки) и
переживают перезапуск и пересборку контейнеров.

## Как проверить всё самому

Пошаговый прогон «с нуля», как это сделал бы новый разработчик.

### 1. Чистый запуск

```bash
./run.sh reset     # удалить старые контейнеры и данные (спросит "yes")
./run.sh           # создать .env, собрать и поднять стек
./run.sh seed      # создать демонстрационные данные
./run.sh creds     # показать логины и пароли
```

Ожидаемо: все четыре контейнера `Up (healthy)`, кроме `worker` (он без
healthcheck), и API отвечает на `/api/v1/health`.

### 2. Проверить API и документацию

```bash
curl -s http://localhost:8080/api/v1/health
curl -s http://localhost:8080/api/v1/openapi.json | head -c 200
```

Откройте в браузере:
- http://localhost:8080 — веб-панель
- http://localhost:8080/api/v1/docs — Swagger UI

### 3. Прогнать проверки

```bash
./run.sh verify    # 57 проверок живого стека → "All stack checks passed."
./run.sh test      # 104 backend-теста → "104 passed"
./run.sh check     # сборка + типы + линтер → без ошибок
./run.sh e2e       # 42 браузерных теста → "42 passed"
```

### 4. Проверить руками основной сценарий

1. Войдите администратором (данные из `./run.sh creds`).
2. **Платежи → Создать**: название «Тестовый сервер», сумма `1500`, валюта
   `RUB`, срок — сегодня. Сохраните.
3. Убедитесь, что платёж появился в таблице, а в календаре появился период.
4. Выйдите и войдите обычным пользователем (`demo_user`).
5. Убедитесь, что виден **тот же** период (общая история).
6. Отметьте оплату. Статус станет «Оплачено» / «Оплачено с просрочкой».
7. Откройте период и **исправьте фактическую дату** на вчерашнюю — статус
   пересчитается, а **срок останется тем же**.
8. Снимите отметку об оплате — период вернётся в прежнее состояние
   (просрочка, если срок прошёл). Запись периода не удаляется.
9. Откройте **Календарь** и **Бюджеты** — данные реальные, из БД.
10. Администратором откройте **Журнал действий** — там видны все действия
    выше.

### 5. Проверить сохранение данных

```bash
docker compose restart
./run.sh verify    # снова 57/57 — данные на месте
```

Или сравните счётчики до и после перезапуска:

```bash
docker compose exec postgres psql -U invoice -d invoice \
  -c "SELECT count(*) FROM payment_occurrences;"
```

### 6. Проверить worker и уведомления

```bash
./run.sh logs worker
```

Если Telegram/SMTP не настроены, worker честно пишет, что канал не настроен и
ничего не имитирует. При наличии токена — отправляет реальные напоминания
(см. раздел «Получение Telegram-токена»).

### 7. Остановить

```bash
./run.sh down      # остановить, данные сохранятся
./run.sh reset     # остановить и удалить данные
```

## Запуск тестов

Самый простой путь — `run.sh`, он сам готовит окружение:

```bash
./run.sh test     # 104 backend-теста (сам поднимает тестовую БД)
./run.sh check    # сборка, типы и линтер frontend
./run.sh e2e      # 42 браузерных теста (нужен запущенный стек + ./run.sh seed)
./run.sh verify   # 57 проверок живого стека по HTTP
./run.sh full     # всё сразу
```

Ниже — те же команды вручную.

### Backend (pytest)

Нужна отдельная PostgreSQL (тесты не трогают рабочую базу):

```bash
docker run -d --name ik-test-pg \
  -e POSTGRES_USER=invoice -e POSTGRES_PASSWORD=invoice -e POSTGRES_DB=invoice \
  -p 55432:5432 postgres:16-alpine

cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
pytest -q          # ожидается: 104 passed
```

Порт и база задаются в `backend/tests/conftest.py` (по умолчанию `55432`,
база `invoice_test` создаётся и удаляется автоматически).

### Frontend (сборка, типы, линтер)

```bash
cd frontend
npm ci
npm run build
npm run typecheck
npm run lint
```

### E2E (Playwright)

Требуется запущенный стек (`./run.sh`) и демонстрационные данные
(`./run.sh seed`).

```bash
cd frontend
npx playwright install chromium
npm run test:e2e   # ожидается: 42 passed
```

Учётные данные E2E берутся из корневого `.env` (те же, что у приложения),
переопределяются переменными `E2E_ADMIN_*` и `E2E_USER_*`.

### Проверка запущенного стека

```bash
./run.sh verify
# или напрямую:
backend/.venv/bin/python scripts/verify_stack.py http://localhost:8080
```

Скрипт проходит реальные HTTP-сценарии: разграничение прав, общий статус,
просрочку, исправление даты, снятие отметки, независимость периодов, бюджеты и
аудит (57 проверок). Учётные данные читаются из `.env`, переопределяются
переменными `VERIFY_ADMIN_*` и `VERIFY_USER_*`. Если демо-данные не созданы,
скрипт прямо об этом скажет и предложит `./run.sh seed`.

## Логи и диагностика

```bash
docker compose logs -f api          # API
docker compose logs -f worker       # планировщик и уведомления
docker compose logs -f frontend     # nginx
docker compose logs -f postgres     # база
```

Типовые проблемы:

| Симптом | Причина и решение |
|---|---|
| API unhealthy сразу после старта | база ещё не готова; подождите, healthcheck повторит попытку |
| Telegram-уведомления не приходят | не заданы `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID`; смотрите предупреждение в логе worker |
| Письма не уходят | не задан `SMTP_HOST`; канал помечен как «Не настроено» |
| Не удаётся войти | проверьте `ADMIN_PASSWORD` в `.env` и логи API |

Журнал уведомлений и причины ошибок доставки хранятся в таблице
`notification_logs` (поле `last_error`, без секретов).

## Ограничения

- **Валюты не конвертируются.** Суммы RUB, USD и EUR всегда показываются
  раздельно; общего итога по разным валютам не существует.
- **Exactly-once для Telegram не гарантируется.** Telegram Bot API не
  транзакционен: если соединение оборвётся после того, как Telegram принял
  сообщение, повторная отправка теоретически возможна. Дубли при повторных
  запусках worker и рестартах исключены идемпотентным outbox с уникальными
  ключами.
- **Реальная доставка в Telegram и email** подтверждается только при наличии
  действующих реквизитов. Без них проверяется логика (mock-транспорт в тестах),
  а внешняя доставка остаётся непроверенной.
- **WebSocket не используется.** Данные обновляются после изменений и при
  возврате на страницу — этого достаточно для продукта.
