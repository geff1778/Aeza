# Демонстрационный сценарий Invoice Keeper

Продолжительность: **4–6 минут**. Сценарий воспроизводим: все записи существуют
в настоящей БД и создаются реальными механизмами приложения.

---

## Подготовка (до демонстрации, ~1 минута)

```bash
cp .env.example .env      # SECRET_KEY и ADMIN_PASSWORD заполнены заранее
docker compose up --build -d
docker compose --profile demo run --rm seed
```

Проверьте, что стек здоров и открывается веб-панель:

```bash
docker compose ps                      # все сервисы healthy
curl -s http://localhost:8080/api/v1/health
```

Откройте http://localhost:8080.

Демонстрационные учётные данные (создаются только профилем `demo`, пароль
переопределяется переменной `DEMO_PASSWORD`):

| Роль | Логин | Пароль |
|---|---|---|
| Администратор | `admin` | значение `ADMIN_PASSWORD` из `.env` |
| Обычный пользователь | `demo_user` | значение `DEMO_PASSWORD` из `.env` |

> Это синтетические данные для демонстрации. На реальном стенде пароль
> администратора меняется в `.env`, а демо-пользователь создаётся вручную.

## Этап 1. Проблема (30 секунд)

**Что показать:** открыть Dashboard.

**Что сказать:** «Компании платят за аренду, серверы и подписки каждый месяц. Кто
оплатил, когда, что просрочено — обычно живёт в таблицах и переписках. Invoice
Keeper собирает это в одном месте: сроки, фактические оплаты, просрочки и общую
историю для всей команды.»

**Что показать:**

- суммы предстоящих платежей **по каждой валюте отдельно** (RUB, USD, EUR);
- сумму просроченных неоплаченных платежей по валютам;
- счётчики «скоро срок» и «просрочено»;

вводил бы в заблуждение.»

## Этап 3. Создание платежа (60 секунд)

**Что показать:** войти администратором → **Платежи** → **+ Новый платёж**.

Заполнить:

- Название: `VPS Server (демо)`
- Сумма: `1500`
- Валюта: `RUB`
- Первый срок: дата через 3–4 дня (чтобы сработало правило напоминания)
- Периодичность: ежемесячно

Нажать **Создать**.

**Что сказать:** «Система сразу создаёт первый период и материализует расписание
на 12 месяцев вперёд. Платёж появился в общей таблице — его видят все
пользователи.»

**Показать:** платёж в таблице; открыть карточку платежа — видны будущие периоды.

## Этап 4. Уведомление (45 секунд)

### Если Telegram настроен

Показать реальное сообщение в Telegram:

> Скоро срок оплаты: VPS Server (демо). Сумма: 1 500 RUB. Срок: <дата>.
> Осталось 3 дня.

Показать inline-кнопку **«Оплачено»**.

**Что сказать:** «Напоминание отправляется за 3 календарных дня. Если платёж
создан, когда до срока осталось меньше трёх дней, уведомление уходит сразу.
По оплаченным и завершённым платежам напоминания не отправляются.»

### Если Telegram не настроен

Не выдавайте mock-сообщение за настоящее. Скажите прямо:

> «Telegram-интеграция требует токена бота. Без токена приложение работает
> штатно, но уведомления не отправляются и не имитируются — на Dashboard канал
> помечен как «Не настроено». Логику напоминаний можно показать в журнале
> уведомлений и в логе worker.»

Показать: Dashboard → «Каналы уведомлений», затем логи:

```bash
docker compose logs --tail=20 worker
```

## Этап 5. Оплата обычным пользователем (60 секунд)

**Что показать:**

1. Выйти. Войти как `demo_user`.
2. Убедиться, что **административных пунктов меню нет** (Пользователи, Журнал

3. Открыть **Платежи** — виден тот же платёж, созданный администратором.
4. Нажать **«Оплачено»**.

**Что сказать:** «Статус платежа общий, он принадлежит периоду, а не пользователю.
Отдельной отметки для каждого пользователя не существует.»

**Показать обновление общего статуса:** выйти, войти администратором, открыть
Платежи — статус тот же. Обновить страницу (F5) — статус сохранился.

Показать фильтр по статусу **Просрочено** — таблица сузилась до просроченных.

## Быстрая проверка после демонстрации

```bash
# данные пережили перезапуск
docker compose restart
docker compose exec postgres psql -U invoice -d invoice \
  -c "SELECT count(*) FROM payment_occurrences;"

# нет дублей периодов и уведомлений
docker compose exec postgres psql -U invoice -d invoice -c "
SELECT count(*) FROM (
  SELECT recurring_payment_id, due_date FROM payment_occurrences
  GROUP BY 1,2 HAVING count(*) > 1
) d;"
```

Обе проверки должны вернуть `0` для дублей и одинаковое число периодов до и после
перезапуска.

## Частые вопросы на демонстрации

**Почему валюты не складываются?**
Без реального курса общий итог был бы фикцией. Курс — отдельная задача, и в
обязательные требования она не входила.

**Что если Telegram недоступен?**
Уведомление помечается как неуспешное с причиной, worker повторит попытку с
задержкой. Приложение продолжает работать.

**Гарантируется ли однократная доставка в Telegram?**
Нет, и мы это честно документируем: Telegram Bot API не транзакционен. Мы
исключили дубли при повторных запусках worker и рестартах через идемпотентный
outbox с уникальными ключами.
