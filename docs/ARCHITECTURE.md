# Архитектура Invoice Keeper

Документ описывает фактическую структуру приложения: компоненты, модель данных,
ключевые правила бизнес-логики и принятые технические решения.

---

## 1. Компоненты

Приложение разделено на независимые процессы, чтобы планировщик уведомлений не
дублировался и не блокировал обработку HTTP-запросов.

| Компонент | Технология | Ответственность |
|---|---|---|
| `frontend` | React 19 + Vite, nginx | SPA, reverse proxy на `/api/` |
| `api` | FastAPI + SQLAlchemy 2 | REST API, сессии, RBAC, аудит, OpenAPI |
| `postgres` | PostgreSQL 16 | Данные, outbox, сессии, аудит |
| `worker` | Python (отдельный процесс) | Генерация периодов, отправка уведомлений, обработка callback |
| `seed` | Python (профиль `demo`) | Идемпотентные демонстрационные данные |

nginx отдаёт статические файлы frontend и проксирует `/api/` на `api:8000`. Это
устраняет CORS: браузер всегда обращается к одному origin.

### Почему worker отдельный

Несколько API-воркеров, каждый со своим планировщиком, отправляли бы уведомления
повторно. Worker запускается одним контейнером и не входит в состав API. Даже при
случайном дублировании worker защита лежит в БД (см. раздел 4).

### Переразрешение DNS-имени upstream

`nginx.conf` использует `resolver 127.0.0.11` и переменную `$api_upstream`.
Без этого nginx кеширует IP контейнера `api` при старте и после перезапуска API
начинает отдавать `502`, пока не будет перезапущен сам. С переменной имя
разрешается на каждый запрос.

## 2. Модель данных

Все таблицы создаются миграциями Alembic. Денежные значения хранятся в
`Numeric(14, 2)` (никогда `float`).

### `users`

| Поле | Тип | Примечание |
|---|---|---|
| `id` | PK | |
| `username` | varchar, unique | логин |
| `email` | varchar, nullable | |
| `password_hash` | varchar | Argon2id, никогда не возвращается |
| `role` | enum | `admin` / `user` |
| `is_active` | bool | деактивированный не может войти |
| `is_bootstrap` | bool | защита bootstrap-администратора |
| `created_at`, `updated_at` | timestamptz | |

### `recurring_payments`

| Поле | Тип | Примечание |
|---|---|---|
| `id` | PK | |
| `title`, `description` | varchar / text | |
| `amount` | Numeric(14,2) | `CHECK amount > 0` |
| `currency` | enum | RUB / USD / EUR |
| `recurrence` | enum | monthly / quarterly / yearly |
| `anchor_day` | smallint | **исходный** день месяца (1–31) |
| `first_due_date` | date | первый срок |
| `is_active` | bool | завершение вместо удаления |
| `created_by_id` | FK → users | создатель |
| `created_at`, `updated_at` | timestamptz | |

Индекс `ix_recurring_active` по `is_active`.

### `payment_occurrences`

| Поле | Тип | Примечание |
|---|---|---|
| `id` | PK | |
| `recurring_payment_id` | FK → recurring_payments | `ON DELETE RESTRICT` |
| `due_date` | date | срок оплаты |
| `amount`, `currency` | Numeric / enum | снимок на момент периода |
| `is_paid` | bool | |
| `paid_at` | date, nullable | фактическая дата |
| `receipt_url` | text, nullable | ссылка на подтверждение |
| `created_at`, `updated_at` | timestamptz | |

Ограничения и индексы:

- `UniqueConstraint(recurring_payment_id, due_date)` — `uq_occurrence_period`.
  Именно это делает генерацию периодов идемпотентной.
- `CHECK amount > 0`.
- `ix_occurrence_due_date` — сортировка и фильтрация по сроку.
- `ix_occurrence_paid_due` — выборки просроченных.

### `notification_logs` (outbox)

| Поле | Примечание |
|---|---|
| `occurrence_id` | FK → payment_occurrences |
| `channel` | telegram / email |
| `kind` | reminder / overdue / paid |
| `status` | pending / sent / failed / skipped |
| `idempotency_key` | **unique** |
| `attempts`, `last_error` | повторные попытки и причина |
| `created_at`, `sent_at` | |

`UniqueConstraint(occurrence_id, channel, kind)` — второе, независимое от
`idempotency_key`, ограничение. Повторный запуск worker не может создать дубль.

### `audit_logs`

`actor_id`, `action`, `object_type`, `object_id`, `payload` (JSONB), `created_at`,
`request_id`. Секреты, хеши паролей, токены и cookie не записываются.

### `budgets`

`period_type` (month/year), `period_key`, `currency`, `limit_amount`.
`UniqueConstraint(period_type, period_key, currency)` — один лимит на
валюту и период. `CHECK limit_amount >= 0`.

### `attachments`

`occurrence_id`, `original_name`, `stored_name` (сгенерированное безопасное имя),
`content_type`, `size_bytes`, `created_by_id`, `created_at`. Файлы лежат в volume
`uploads_data`, раздаются только через авторизованный endpoint.

### Сессии

Серверные сессии с непрозрачным идентификатором. Хранятся в БД, cookie —
`HttpOnly`, `SameSite=Lax`, `Secure` в production. Logout удаляет запись сессии,
поэтому старый cookie становится бесполезен.

## 3. Бизнес-логика

### Статус — единый источник

`app/services/status.py` — единственное место, где вычисляется статус. Веб-панель,
API, worker и Telegram-callback используют одну и ту же функцию, поэтому
расхождений быть не может.

```
не оплачено, сегодня > срок        → overdue
не оплачено, 0 <= дней до срока <= 3 → due_soon
не оплачено, дней больше           → pending
оплачено, paid_at <= due_date      → paid_on_time
оплачено, paid_at >  due_date      → paid_late
```

Статус принадлежит **периоду**, а не пользователю. Отдельной таблицы отметок для
каждого пользователя не существует — это ключевое требование.

### Календарная арифметика

`app/services/dates.py` хранит `anchor_day` — исходный день месяца. Функция
`add_months_anchored` переносит дату на N месяцев вперёд и **прижимает** день к
последнему дню месяца, если он короче:

```
31 января  →  28/29 февраля  →  31 марта  →  30 апреля  →  31 мая
```

День не «залипает» на 28 после февраля, потому что следующий период считается
всегда от исходного `anchor_day`, а не от предыдущего периода.

### Генерация периодов

- При создании регулярного платежа создаётся первый период.
- При старте приложения и по расписанию worker материализует недостающие периоды
  на горизонт `GENERATION_HORIZON_MONTHS` (по умолчанию 12).
- Вставка идёт через `INSERT ... ON CONFLICT DO NOTHING` по
  `(recurring_payment_id, due_date)`, поэтому повторный запуск безопасен.
- Для завершённого платежа (`is_active = false`) новые периоды не создаются.
- Оплата одного периода никак не влияет на генерацию и статус других.

### Завершение вместо удаления

`DELETE /recurring-payments/{id}` выставляет `is_active = false`. Прошлые периоды
остаются в БД и в истории, будущие периоды не создаются, напоминания не
отправляются. Внешний ключ `ON DELETE RESTRICT` дополнительно защищает историю от
случайного каскадного удаления.

### Часовой пояс

`APP_TIMEZONE` (по умолчанию `Europe/Moscow`). Бизнес-даты (`due_date`, `paid_at`)
интерпретируются в этой зоне; технические метки времени хранятся в UTC. Функция
`local_today(tz)` даёт «сегодня» в нужной зоне, поэтому контейнер в UTC и
пользователь в Москве видят одинаковую дату.

## 4. Уведомления

### Решение и доставка разделены

`app/services/notifications.py` только **решает**, что нужно уведомить, и
складывает задачу в outbox. Транспорты (`telegram.py`, `email.py`) доставляют то,
что уже лежит в outbox. Правила не дублируются между каналами: добавление email
не потребовало второй копии логики.

### Правила

| Условие | Поведение |
|---|---|
| Не оплачено, до срока ≤ 3 дней | reminder |
| Не оплачено, срок уже прошёл | overdue |
| Платёж оплачен | ничего не отправляется |
| Регулярный платёж завершён | ничего не отправляется |
| Уже была успешная отправка этого типа | повторно не отправляется |

Немедленное уведомление для только что созданного периода — следствие первого
правила: если до срока меньше трёх дней, напоминание ставится в очередь сразу.

### Защита от дублей

Три независимых уровня:

1. `idempotency_key` (unique) — уникальный ключ на период + канал + тип.
2. `UniqueConstraint(occurrence_id, channel, kind)`.
3. Атомарный захват задачи: worker переводит строку из `pending` в `sending`
   условным `UPDATE ... WHERE status = 'pending'`, поэтому два процесса не возьмут
   одну задачу.

Повторные попытки — экспоненциальная задержка, ограниченное число попыток
(`WORKER_MAX_ATTEMPTS`, по умолчанию 5), после чего задача помечается `failed` с
сохранённой причиной.

### Ограничение exactly-once

Telegram Bot API не транзакционен. Если соединение оборвётся уже после того, как
Telegram принял сообщение, повторная отправка теоретически возможна. Приложение
минимизирует окно и документирует ограничение вместо ложного обещания
гарантированной однократной доставки.

### Inline-кнопка «Оплачено»

Callback содержит только идентификатор периода (доверенное серверное значение).
Сумма, валюта и срок из callback не принимаются. Обработчик проверяет chat ID
(и `TELEGRAM_ALLOWED_USER_IDS`, если задан), вызывает тот же сервис бизнес-логики,
что и веб-панель, пишет аудит и отвечает на callback. Повторное нажатие
идемпотентно: платёж уже оплачен — состояние не меняется.

## 5. Безопасность

- Пароли — Argon2id. Хеш никогда не покидает БД.
- Серверные сессии с непрозрачным ID, cookie `HttpOnly` + `SameSite=Lax`.
- CSRF-токен обязателен для изменяющих запросов (`X-CSRF-Token`).
- RBAC проверяется на сервере в `app/api/deps.py`. Скрытие кнопок в React —
  только удобство, не защита.
- Ограничение частоты входов (`LOGIN_RATE_LIMIT`, по умолчанию 10 попыток за 300 с).
- Валидация входных данных схемами Pydantic v2.
- SQL — только через ORM и параметризованные запросы. Сортировка в списке периодов
  whitelisted (`due_date` / `amount` / `created_at`), имя колонки из запроса в SQL
  не попадает.
- Загрузка файлов: проверка MIME и расширения, ограничение размера, безопасное
  сгенерированное имя, защита от path traversal, файлы не исполняются и не
  раздаются статически.
- Обработчик ошибок возвращает клиенту обезличенное сообщение и `request_id`, не
  раскрывая traceback, SQL и конфигурацию.
- Healthcheck показывает состояние БД и часовой пояс, но не переменные окружения.

## 6. Что сознательно не используется

- **Redis / брокер сообщений** — outbox в PostgreSQL закрывает задачу без
  дополнительного сервиса.
- **Kubernetes** — Docker Compose достаточно для продукта такого размера.
- **WebSocket** — данные обновляются после мутаций и при возврате на страницу;
  real-time не требуется продуктовым сценарием.
- **Конвертация валют** — вне области задачи; суммы разделены по валютам.
